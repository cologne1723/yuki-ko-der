## 문제 설명

### 출제자용 참고 사항 (2026/05/10 업데이트)

특수 저지 및 리액티브 문제의 검증 코드 실행 사양입니다.

실행 명령은 다음과 같습니다.

```text
    실행 명령 (문제 입력 파일 경로) (문제 출력 파일 경로) (제출된 소스 코드 경로) (점수 파일 경로)

    (표준 입력에는 제출 코드의 표준 출력이 전달됩니다)
```

실행 명령의 예는 다음과 같습니다.

```text
    ./a.out test_in/1.txt ans/1.txt main.ws score/1.txt < out/1.txt
```

[검증 코드 구현 예](https://yukicoder.me/wiki/howtojudge)

검증 코드에서 주의할 점은 제출 코드의 표준 출력에 언어에 따라 `CR`(개행 코드: 캐리지 리턴)이 포함될 수 있다는 것입니다. 가능한 한 이에 대응해 주세요.

특히 C++의 `std::getline`은 저지 환경에서 `CR`을 해석하지 못합니다.

`std::getline`에 관한 [참고 메모](http://luluci.blog44.fc2.com/blog-entry-45.html)도 확인해 주세요. 이와 같이 다른 `CR` 미대응 사례가 있다면 제안해 주세요.

위 형식으로 실행됩니다. 즉, 인자는 $4$개 이상이며(앞으로 늘어날 가능성이 있습니다), 검증 코드가 런타임 오류(Exit Code가 $0$이 아님. 예를 들어 `assert` 등으로 종료)가 되면 `WA`가 됩니다.

검증 코드가 TLE이 되면 `J_TLE`이 되지만, 가능한 한 발생하지 않도록 해 주세요.

리액티브 저지에서 검증 코드가 런타임 오류이고 사용자 코드가 TLE인 경우에는 `WA`가 됩니다.

Exit Code를 $100$으로 하여 프로그램을 종료하면 `QLE`이 됩니다. (2019/11/14 추가, 임시안)

그 밖의 `RE`나 `TLE` 등의 판정에는 일반 체커가 사용됩니다.

특수 저지와 리액티브 모두 **테스트 출력 파일을 준비해 주세요**. 빈 파일($0$바이트 파일)이면 충분하지만, 해답의 $1$개 예를 넣어 두는 것도 좋을 수 있습니다.

리액티브 문제의 검증 코드에 대한 입력은 문제의 테스트 입력 파일에 넣어 주세요.

검증 코드의 표준 오류 출력은 자유롭게 사용해도 됩니다.

### 리액티브 문제에 관하여

리액티브 문제에서는 저지 코드와 풀이 프로세스가 표준 입출력을 통해 **양방향으로 실시간 통신**합니다. FD0/FD1의 의미는 특수 저지와 같지만(FD0에는 풀이의 stdout이, FD1에서는 풀이의 stdin으로 연결됨), 파일을 통한 배치 방식이 아니라 실시간 파이프로 연결된다는 점이 다릅니다.

- `FD0` (stdin): 풀이 프로세스의 stdout에 연결됩니다(풀이가 출력한 내용을 저지가 읽습니다).
- `FD1` (stdout): 풀이 프로세스의 stdin에 연결됩니다(저지가 풀이 프로세스에 입력을 보냅니다).
- `FD2` (stderr): 자유롭게 사용할 수 있습니다(로그 출력 등).

테스트 입력 파일의 내용은 **표준 입력으로 전달되지 않습니다**(특수 저지도 마찬가지이며, FD0은 풀이 프로세스의 출력이 사용합니다). 필요한 경우 명령줄 인자로 전달되는 입력 파일 경로(`argv[1]`)를 열어 읽어 주세요.

출력한 뒤에는 버퍼링으로 데드록이 발생할 수 있으므로 반드시 `flush()`해 주세요.

리액티브 문제는 순수 코드 판정을 하지 않습니다.

### 통신 문제에 관하여

통신 문제는 리액티브 형식의 일종으로, **같은 프로그램이 $2$개 프로세스에서 실행**됩니다.

저지 코드(검증 코드)가 각 프로세스의 입출력을 파이프로 중개하고 프로세스 간 통신을 제어합니다.

### 파이프 구성

저지 프로세스의 표준 입출력(FD0~2) 취급은 다음 $3$가지 형식에서 서로 다릅니다.

| FD | 특수 저지 (파일) | 리액티브 (실시간) | 통신 |
| --- | --- | --- | --- |
| `FD0` (stdin) | 풀이 프로세스의 출력 파일 | 풀이 프로세스의 stdout | 프로세스 $1$의 stdout |
| `FD1` (stdout) | 저지 출력 (자유) | 풀이 프로세스의 stdin | 프로세스 $1$의 stdin |
| `FD2` (stderr) | 자유 | 자유 | 자유 |
| `FD3` | ― | ― | 프로세스 $2$의 stdout (저지가 읽음) |
| `FD4` | ― | ― | 프로세스 $2$의 stdin (저지가 씀) |

특수 저지는 풀이 프로세스가 종료된 뒤 그 출력 파일이 FD0에 전달되는 파일 기반 실행입니다. 리액티브는 저지와 풀이 프로세스가 동시에 실행되고 FD0/FD1이 그대로 파이프로 연결되는 실시간 대화 형식입니다. 통신은 리액티브의 확장으로, 프로세스 $1$과는 FD0/FD1(리액티브와 동일)로, 프로세스 $2$와는 FD3/FD4로 통신합니다. 테스트 입력은 어떤 형식에서도 `argv[1]`에서 읽습니다.

통신 문제에서는 저지 프로세스에 다음 파일 디스크립터(FD)가 할당됩니다.

프로세스 $1$의 FD1 (stdout) ──→ FD0 (저지가 읽음)  
프로세스 $1$의 FD0 (stdin)  ←── FD1 (저지가 씀)  
프로세스 $2$의 FD1 (stdout) ──→ FD3 (저지가 읽음)  
프로세스 $2$의 FD0 (stdin)  ←── FD4 (저지가 씀)

사용자 프로세스 입장에서는 평소와 같이 FD0/FD1(stdin/stdout)입니다. 저지 입장에서는 프로세스 $1$과는 표준 입출력(FD0/FD1)으로, 프로세스 $2$와는 FD3/FD4로 통신합니다.

| FD | 방향 | 연결 대상 | 용도 |
| --- | --- | --- | --- |
| `FD0` (stdin) | 읽기 | 프로세스 $1$의 stdout | 프로세스 $1$이 출력한 데이터를 저지가 읽음 |
| `FD1` (stdout) | 쓰기 | 프로세스 $1$의 stdin | 저지가 프로세스 $1$에 데이터를 보냄 |
| `FD3` | 읽기 | 프로세스 $2$의 stdout | 프로세스 $2$가 출력한 데이터를 저지가 읽음 |
| `FD4` | 쓰기 | 프로세스 $2$의 stdin | 저지가 프로세스 $2$에 데이터를 보냄 |

저지 코드는 FD0/FD1(프로세스 $1$)과 FD3/FD4(프로세스 $2$)로 $2$개의 사용자 프로세스와 통신합니다.

인자 형식은 리액티브와 같습니다. 테스트 입력이 필요하다면 `argv[1]`을 열어 읽어 주세요.

사용자 프로세스는 평소와 같이 표준 입력(`stdin`)에서 읽고 표준 출력(`stdout`)에 씁니다. FD 번호를 의식해야 하는 것은 저지 코드 쪽뿐입니다.

### 저지 코드 구현 예 (Python)

프로세스 $1$은 표준 입출력(FD0/FD1)을, 프로세스 $2$는 FD3/FD4를 사용합니다. 프로세스 $1$은 `sys.stdin`/`sys.stdout`을 사용해도 되고, FD 번호를 명시하는 `os.fdopen()`을 사용해도 됩니다.

#### 작성 방법 $1$: `sys.stdin` / `sys.stdout` 사용 (리액티브와 같은 방식)

```python
import os, sys

# プロセス1: 標準入出力で通信
user1_read  = sys.stdin              # プロセス1の出力を読む
user1_write = sys.stdout             # プロセス1に入力を送る

# プロセス2: FD3/FD4で通信
user2_read  = os.fdopen(3, 'r')      # プロセス2の出力を読む
user2_write = os.fdopen(4, 'w')      # プロセス2に入力を送る

# テスト入力は argv[1] から
with open(sys.argv[1]) as f:
    test_input = f.read()

user1_write.write("1 ...\n")
user1_write.flush()
user2_write.write("2 ...\n")
user2_write.flush()
```

#### 작성 방법 $2$: 모두 `os.fdopen()`으로 통일 (프로세스 $2$와 작성 방법 통일)

```python
import os, sys

# プロセス1・プロセス2 を同じスタイルで開く
user1_read  = os.fdopen(0, 'r')      # FD0: プロセス1の出力
user1_write = os.fdopen(1, 'w')      # FD1: プロセス1への入力
user2_read  = os.fdopen(3, 'r')      # FD3: プロセス2の出力
user2_write = os.fdopen(4, 'w')      # FD4: プロセス2への入力

with open(sys.argv[1]) as f:
    test_input = f.read()

user1_write.write("1 ...\n")
user1_write.flush()
user2_write.write("2 ...\n")
user2_write.flush()
```

$2$가지 방법 모두 동일하게 동작합니다. `sys.stdin`은 내부적으로 FD0을 가리키므로 작성 방법 $1$과 작성 방법 $2$는 동등합니다. 프로세스 $1$과 프로세스 $2$의 대칭성을 강조하려면 작성 방법 $2$를, 리액티브와의 일관성을 중시한다면 작성 방법 $1$을 선택하면 됩니다.

통신 문제의 저지 코드 구현에서는 다음 사항에 주의해 주세요.

- 프로세스 $1$과는 표준 입출력(FD0/FD1)으로, 프로세스 $2$와는 FD3/FD4로 통신합니다.
- 테스트 입력은 `argv[1]`에서 읽습니다(stdin은 프로세스 $1$에 사용됩니다).
- 쓴 뒤에는 반드시 `flush()`합니다.
- $1$개의 프로세스가 잘못된 출력을 했을 때 다른 프로세스가 데드록에 빠지지 않도록 처리합니다.
- 메모리 사용량은 $2$개의 사용자 프로세스 중 최댓값으로 판정됩니다.
- 사용자 프로세스 중 어느 $1$개가 비정상 종료하면 그 종료 코드가 사용됩니다.

통신 문제는 순수 코드 판정을 하지 않습니다.

### 점수에 관하여 (β)

문제 편집 페이지에서 문제 종류로 ‘점수 문제’를 선택하면 문제 페이지 상단에 ‘점수순’ 탭이 표시됩니다.

‘점수순’ 탭에는 AC인 제출 중 각 사용자의 최고점 제출(동점이면 제출 ID가 작은 제출)이 표시됩니다.

점수 문제에는 임시로 제출 제한이 있어, 같은 문제의 마지막 제출(CE 제외) 후 $5$분 이내에는 제출할 수 없습니다.

이때 점수 파일에 출력한 값이 점수가 되어 각 테스트 케이스의 합계로 집계됩니다.

점수 파일에는 부호 있는 $64$비트 정수 값을 출력해 주세요. (끝의 개행도 허용됩니다.) 합계도 오버플로하지 않도록 주의해 주세요.

$64$비트 정수 값을 사용할 수 있지만 자릿수가 많으면 보기 어려우므로, 많아도 $9$자리 정도가 바람직합니다.

점수를 작은 순서로 나타내고 싶다면 그 내용을 문제문에 명시하고, 값에 마이너스를 곱하면 됩니다.

대부분은 특별히 의식하지 않고 파일을 열어 쓰면 되지만, ‘기타 사용자’에게 쓰기 권한을 주지 않도록 주의해 주세요.

점수 문제로 설정하면 자동으로 ‘AC 공개’를 하지 않도록 설정됩니다.

점수 문제의 난이도는 $0$으로 설정하면 됩니다.

점수 문제는 순수 코드 판정을 하지 않습니다.
