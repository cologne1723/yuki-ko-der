# 문제 번역 서브에이전트 실행

사용자가 지정한 모델을 `model`에 그대로 전달한다. 생략하면 부모 모델을 상속하므로
금지한다. 요청 모델을 사용할 수 없으면 실패를 보고한다. 다른 모델로 대체하거나
모델이 바뀌었다고 추측해서 말하지 않는다.

## 실행 단위와 병렬 개수

- 문제 하나당 서브에이전트 하나. 작업 식별명은 `translate_<problemNo>`이다.
- 사용자가 한 문제 시험을 요청하면 **1개만** 실행한다.
- 여러 문제 번역을 명시적으로 위임하면 **최대 6개**를 병렬 실행한다.
  사용자가 더 적은 개수를 지정하면 그 수를 따른다. 남은 문제는 자리가 날 때 배정한다.
  완료된 에이전트도 닫기 전에는 슬롯을 차지하므로 검증 후 닫고 다음 문제를 배정한다.
- 서로 다른 문제만 배정한다. 같은 파일을 두 에이전트가 수정하지 않게 한다.
- 실행 전 원문 파일과 번역 파일 유무를 확인한다. 기존 번역은 미번역 작업에 배정하지 않는다.

## 정확한 생성 호출

아래는 셸 명령이 아니라 `functions.exec`에서 실행하는 도구 호출이다.
도구가 보이지 않으면 `ALL_TOOLS`에서 `multi_agent_v1__spawn_agent`를 찾아
현재 스키마와 지원 모델을 확인한다. CLI 중첩 실행으로 대체하지 않는다.

사용자가 `gpt-5.6-luna`를 지정한 경우 다음처럼 모델과 추론 강도를 명시한다.
추론 강도는 사용자 지정값을 우선하고, 미지정이면 `medium`을 쓴다.

```js
const problemNo = 2805; // 실제로 미번역인지 확인한 번호
const result = await tools.multi_agent_v1__spawn_agent({
  model: "gpt-5.6-luna",
  reasoning_effort: "medium",
  fork_context: false,
  message: `작업 식별명: translate_${problemNo}.
/Users/hyea/yukicoder에서 문제 ${problemNo} 하나를 한국어로 번역한다.
problem-translations/WORKFLOW.md에서 시작해 단계별 지침을 작업 직전에 읽는다.
수정 범위는 problem-translations/ko/problems/${problemNo}.mdx 하나다.
지금은 1단계만 수행한다: 01-source.md와 02-meaning.md에 따라 원문·glossary를 확인한다.
파일을 쓰지 말고 식별자·미확정 이름·가장 헷갈리는 조건과 예제 근거를 5줄 이내로 보고한다.
승인·커밋·배포하지 않는다.`,
});
text(`Spawned ${result.agent_id} (gpt-5.6-luna medium)`);
text({ task: `translate_${problemNo}`, nickname: result.nickname });
```

`Spawned`는 생성 호출이 성공한 뒤에만 표시한다. 문자열의 모델·추론 강도는 실제
호출 인수와 같아야 한다. 자동 배정된 `nickname`은 작업 식별명이나 모델과 다르다.
도구에는 사용자 지정 nickname 인수가 없으므로 이름을 바꿨다고 주장하지 않는다.

## 여러 문제 배정

컨텍스트는 `fork_context: false`로 시작하고 AGENTS.md 본문을 메시지에 복사하지 않는다.
이 옵션이 런타임의 공통 지침 자동 전달까지 차단한다는 의미는 아니다.

초기 지시는 담당 문제·수정 범위·지침 진입점만 전달한다. 규칙 본문을 프롬프트에
복사하지 않는다. 재지시는 실패 위치·관찰 결과·확인 방법만 전달하고 전체 지시를 반복하지 않는다.

위 호출을 문제 번호를 인수로 받는 함수로 만들고, 서로 다른 번호 최대 6개에 대해
`Promise.allSettled`로 동시에 호출한다. 각 성공 결과의 `agent_id`와 문제 번호를
저장하고 위 `Spawned` 형식으로 출력한다. 실패한 생성은 실패로 기록하며 다른
성공한 작업을 중복 생성하지 않는다.

## 완료 확인

단계별 읽기를 한 번의 요청에만 맡기지 않는다. 문제당 같은 에이전트를 유지하며
각 단계의 완료를 기다린 뒤 다음 메시지를 보낸다. 문제별 진행은 독립적이며 최대 6개다.
1단계 보고는 번역 완료가 아니다. 단계 사이에 에이전트를 닫거나 새로 생성하지 않는다.

```js
await tools.multi_agent_v1__send_input({
  target: agentId,
  message: "2단계: 02-meaning.md와 03-structure-and-format.md를 지금 다시 읽고 담당 MDX를 작성한다. 저장본을 다시 읽고 변경 경로만 보고한다. 아직 완료 선언하지 않는다.",
});
// 이 에이전트의 2단계 완료를 wait_agent로 확인한 뒤에만 호출한다.
await tools.multi_agent_v1__send_input({
  target: agentId,
  message: "3단계: 04-verification.md를 지금 다시 읽는다. 원문과 저장본 전체를 대조하고 모든 검사를 실행한다. 발견한 오류를 직접 수정하고 재검사한다. 검사 결과·저장본의 핵심 조건 한 문장과 대응 예제·미확정 항목만 간단히 보고한다.",
});
```

실제 준수 여부는 3단계 이후 저장본으로 판정한다. 단계별 메시지에는 규칙 본문이나
원문 전체를 붙이지 않는다. 부모가 내용 수정을 지시했다면 수정 후 통과와 구분해 기록한다.

- 작업 중에는 주 에이전트가 검사 준비 등 겹치지 않는 일을 한다.
- 결과가 필요한 시점에 `multi_agent_v1__wait_agent`로 저장한 ID를 기다린다.
  타임아웃은 실패가 아니며 같은 ID를 계속 관찰한다.
- 재지시는 `multi_agent_v1__send_input`을 사용한다. 같은 작업을 새로 생성하지 않는다.
- 완료 보고만 믿지 말고 실제 파일, 입력 수식, 원문 예제와 glossary 적용을 확인한다.
- `pnpm check:translation -- 번호1,번호2,...`도 직접 실행한다. 실패한 배치는 완료가 아니다.
- 최초 완료 보고 시 결과와 수정 후 결과를 구분한다. 부모가 반복 오류를 고친 배치를
  규칙 준수 시험의 성공으로 기록하지 않는다.
- 실패 사례와 검사 범위를 기록한다. 한 문제 통과로 전체 규칙 준수를 보장하지 않는다.
- 필요한 검증이 끝나면 `multi_agent_v1__close_agent`로 해당 에이전트를 닫는다.
